# Preludio Roadmap

更新日期：2026-10-24。按里程碑和退出条件推进，不预设交付日期。产品要求见 [Spec](spec.md)，职责与技术决策见 [Architecture](architecture.md)。

## 1. 推进原则

先用一个模型、一组明确的观测和一个本地后端建立可复现链路，再接入 Radiust。macOS 和 Web 都是首批目标，但尚未决定产品交付的先后；当前 CPU spike 提供数值参考，Conv3D 的浏览器兼容性决定 Web 需要单独验证。

原讨论中的 Rust + TypeScript、Core ML、Tauri 和跨平台目录树作为候选保留。实现一个经验证的路径以后，再决定是否值得维护第二条路径或提取共享核心。

## 2. 里程碑总览

| 里程碑 | 状态 | 依赖 | 退出条件 |
| --- | --- | --- | --- |
| M0：模型部署 spike | 已完成，限 CPU 数值验证 | 临时 checkpoint 与训练配置 | 导出产物、参考输入输出、误差报告和复现说明齐全 |
| M1：确认数据与模型包契约 | 下一步 | M0、训练数据来源说明、Radiust 候选来源 | 编码、网格、时间与缺测策略有证据；选定可接入来源；模型包契约可校验 |
| M2：原生运行时与 macOS 验证 | 待开始 | M0；完整输入链路依赖 M1 | 一个无需训练环境的本地调用路径，通过参考样本、输入校验与目标设备预算 |
| M3：Radiust 首次完整接入 | 待开始 | M1、M2；若 Web 先成熟，可采用 M4 的已验证路径 | 一种真实来源完成获取、转换、本地预测、正确时间与网格展示 |
| M4：Web 可行性与交付 | 待开始，可提前做算子实验 | 算子实验只需 M0；完整接入需要 M1 | 选定浏览器和模型组合通过兼容性、数值、内存、性能与本地运行检查 |
| M5：移动端与手表 | 延后 | 至少一个消费端闭环及设备需求 | 单独定义设备、模型和资源预算后再排期 |

M1 与 M2 的张量级运行时工作可以并行。M4 的兼容性试验也不必等待 Radiust UI；它用于尽早判断是否需要更适合浏览器的模型。生产可用性还需要贯穿 M1 至 M3/M4 的气象效果评估。

- [x] 用 AZ9002 的四帧真实灰度观测构造输入，保存 PyTorch 与 ONNX 结果。
- [x] 定位 GroupNorm 默认导出误差，用逐轴归约导出保持 CPU 精度，并保留回归测试。
- [x] 留下导出工具、四项 Python 测试和[复现文档](ghost-unet3d.md)。

## 4. M1：先把数据含义确认下来

需要交付的内容：

1. 追溯 PNG 生成方式，确认灰度与物理量的映射、截断或分级方式，以及缺测与无回波编码；保留可核查样本。
2. 确认训练样本的站点网格、投影、范围、像元方向和缩放后的空间关系，明确能否接收目标 Radiust 来源。
3. 固定观测时间规则与异常策略；当前模型要求四帧、六分钟间隔，尚无补帧策略。
4. 定义最小的版本化模型包契约，覆盖模型身份、tensor、预处理、输出解释、支持后端及参考样本；记录原始输入来源与哈希。
5. 增加至少覆盖有效序列、缺帧、错时、错网格和不兼容编码的契约验证样本。

完成条件：从选定的观测来源出发，可以解释并复现每一步数值与空间转换；不能只证明 `.npy` 能送进模型。如果目标来源与训练编码不兼容，应明确采用可验证的转换、换模型或重新训练，不能以“都在 `[0,1]`”代替兼容证明。

## 5. M2：最小原生运行时与目标设备测量

工作方案是先在现有 Rust crate 内提供一个本地模型调用路径，ONNX Runtime CPU 作为已有证据的基线。Rust 绑定和依赖版本尚未选定；只有出现实际复用需求时才拆 crate。

交付模型加载、契约校验、模型专用预处理、推理、输出校验和来源元数据。用固定张量先证明运行时与参考一致，再用 M1 的原始观测证明完整转换链路一致；包含错误输入与模型哈希不符的检查。

在基准测试前选定 macOS 设备及可接受的延迟、内存和体积预算。记录冷启动、热推理、多次运行分布、峰值内存、线程、系统和引擎版本，并验证会话复用与应用交互。Linux 的 4.097 秒不能替代这些测量。

Core ML 可以作为加速实验。必须记录实际执行路径、CPU 回退情况、误差与收益；若覆盖率或收益不够，保留 CPU 基线。模型裁剪、量化或算子转换都要产生新的验证记录。

完成条件：无需 Python / Onix 训练环境，能在目标 macOS 设备运行固定样本，满足预先确定的预算和 Spec 的数值、错误与来源要求。

## 6. M3：接入 Radiust

先核对 Radiust 当时的数据类型和来源实现，编写薄适配层，不直接把演进中的 `RadarField` 作为 Preludio 的公共依赖。选一个编码、网格和质量信息均明确的来源完成以下链路：

```text
Radiust 获取与解码 → 同网格观测序列 → Preludio 本地预测
    → 带有效时间和来源的预测场 → Radiust 地图与时间轴
```

展示应包括观测与预测的边界、最后观测时间、各预测有效时间、模型身份及失败状态。UI 技术栈在该阶段选定；Tauri + TypeScript 是原讨论中的候选，尚未实施。

完成条件：一种真实来源可以重放与本地运行，预测与地图对齐，错时或缺测得到可解释处理，观测和预测不会混淆。若只完成技术演示，必须说明气象效果尚未验收，不能据此宣传两小时有效预报。

## 7. M4：浏览器单独验证

当前 GhostUNet3D 含 Conv3D。截至 2026-10-24，ONNX Runtime Web 的[官方 WebGPU 算子表](https://github.com/microsoft/onnxruntime/blob/main/js/web/docs/webgpu-operators.md)将 Conv3D 标为不支持。因此先解决模型 / 后端兼容性，再承诺 Web 产品路径。

可分别验证当前模型的 WASM CPU 路径，以及适配 WebGPU 的模型或算子转换。每次实验记录浏览器、系统、设备、后端、图分配或回退、加载错误、数值差异、延迟和峰值内存；WASM 也必须实测，不能视为已可用的兜底。

只有通过验证才增加 TypeScript Web 入口。网页的数据获取、权限和跨域策略由消费者明确；本地样本可先用于排除数据获取的干扰。扩展的权限、打包与运行生命周期另行验证。

完成条件：至少一个明确的浏览器 / 模型 / 后端组合通过契约、参考与设备预算检查，准备好模型和观测后能断网执行，并通过相同来源的集成验证。若不通过，记录阻碍与模型调整方向，保留已经验证的原生路径。

## 8. 效果评估与后续扩展

M1 起建立独立的天气过程评估集，覆盖无回波、不同强度、发展和消散等情况。先定义逐时效指标与对照基线，再评估发布候选模型；数值对齐报告与气象效果报告分别保存。模型仍在训练，后续 checkpoint 必须重新导出、比较和评估，不沿用 step 22000 的结论。

M5 先选择一个有明确用户需求的移动平台，验证模型转换、资源预算和效果；Swift / Core ML、Kotlin / LiteRT 等仍是候选。手表可以先探索手机计算后展示结果，是否需要独立小模型由设备实测和产品需求决定。降雨概率、开始时间与通知都需要额外定义和评估。

## 9. 下一次工作的具体起点

优先追溯训练 PNG 的生成链路，并挑选一个 Radiust 数据来源确认映射关系。同时可以用现有固定 `.npy` 开始最小 Rust CPU 调用和浏览器算子试验；在 M1 通过前，这些都只属于张量级部署实验。
